# 领域资料

叶巴滩电站以集鱼槽、155 米轨道提升、无人车陆运和运鱼船船运帮助本土鱼类越过高坝。
本服务围绕“运输箱清点数与最终放流数对不上”的问题，建立一条贯穿五个环节的批次核验链路：

```
分拣 SORTING → 155米轨道提升 HOIST_155M → 陆运 LAND_TRANSPORT
             → 船运 VESSEL_TRANSPORT → 放流 RELEASE
```

## 数量守恒与短数阻断

- 每个鱼批（`fish_lot`）登记时必须声明来源：`WILD`（天然野生过坝鱼）或 `HATCHERY`（增殖站鱼苗）。
- 每段交接逐箱登记运输箱（`container_ref`）的发出数，箱量合计必须等于系统按上一段实收算出的“守恒应发数”，杜绝无记录的增减。
- 接收方逐箱清点。清点相符即配平（`BALANCED`）；出现短数则交接进入 `BLOCKED`，**上一段未配平不得登记下一段交接**，从而把损耗锁定在具体环节与箱体。
- 短数只能由两种凭证解释：
  - `DEATH` 死亡记录；
  - `RESORT` 重新分拣记录（必须指定并入的目标批次 `to_lot_code`，确认时在转出/转入两个批次上同时留下正负台账）。
- 凭证初始为 `PENDING`，经确认（`CONFIRMED`）后才具备守恒效力；被驳回（`REJECTED`）不放行。凭证数量不得超过本环节短数。
- 设备故障（提升机、无人车、运鱼船等）单独登记，用于解释异常背景，**不能抵减短数**。
- 放流环节配平后还必须登记放流地点，批次才转为 `RELEASED`。

批次守恒账：`期初数 + 重分拣并入 − 重分拣转出 − 已确认死亡 = 放流/在链数`。

## 标记、回捕与放流成效

- 增殖鱼苗在放流前登记耳石（`OTOLITH`）或荧光（`FLUORESCENT`）标记及其 `marker_code`；野生批次禁止登记标记。
- 数月后的回捕调查（`surveys`）逐条登记检出：
  - 带标记且命中已登记增殖标记 → `CREDITED`，自动关联到具体批次并计入该批放流成效；
  - 无标记天然鱼 → `WILD`，并列展示但**不计放流成效**；
  - 有标记却查无此标记批次 → `UNMATCHED_MARK`，不计成效，留待人工核查。

管理部门通过批次全链路查询（`GET /v1/lots/{lot}/trace`）一次看清：每段交接的应发/实收/短数与状态、
凭证及其确认人、重分拣台账、设备故障、放流地点与时间，以及数月后按标记关联的监测证据。

## 数据约定

`contracts/entities.json` 保存外部数据交换字段与枚举；`fixtures/example.json` 给出各关键报文的
脱敏示例（示例不包含真实个人资料）。运行时持久化文件由 `DATABASE_PATH` 决定（默认 `data/app.sqlite3`）；
时间字段使用带时区偏移的 ISO 8601 字符串，纯日期 `YYYY-MM-DD` 亦接受。来源编号仅表示提交方对同一记录的识别符。

迁移 SQL 嵌入在服务二进制中（`internal/store/migrations/`），服务启动自动应用，
`cmd/migrate` 可单独执行迁移；SQLite 驱动为纯 Go 的 `modernc.org/sqlite`，支持无 CGO 静态构建。
